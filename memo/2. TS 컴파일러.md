## 0. TS의 시작
TypeScript는 Microsoft가 개발한 오픈 소스 프로그래밍 언어로, 2012년에 처음 공개되었다. JavaScript는 동적 타입 언어이기 때문에 실행 전 타입 오류를 발견하기 어렵고, 프로젝트 규모가 커질수록 코드의 안정성과 유지보수성이 떨어질 수 있다. TypeScript는 이러한 문제를 해결하기 위해 JavaScript에 정적 타입 검사와 인터페이스 등의 기능을 추가했다. TypeScript 코드는 브라우저나 Node.js에서 직접 실행되지 않고, 컴파일 과정을 거쳐 JavaScript로 변환된다. 또한 JavaScript의 상위 집합(Superset)이므로 기존 JavaScript 생태계를 활용하면서 점진적으로 도입할 수 있다. 현재는 React, Vite, NestJS 등 다양한 프론트엔드 및 백엔드 프로젝트에서 널리 사용된다.


## 1. TypeScript의 구성 요소

TypeScript는 JavaScript에 정적 타입 시스템을 추가하고 개발 도구 지원을 강화한 프로그래밍 언어다.

TypeScript의 주요 구성 요소는 다음과 같다.


### 1.1 프로그래밍 언어

JavaScript의 문법을 기반으로 타입 표기, 인터페이스, 제네릭 등 추가적인 기능을 제공한다.

```typescript
const name: string = "Jade";
const age: number = 20;

function greet(name: string): string {
  return `Hello, ${name}`;
}
```

위 코드에서 `: string`, `: number`는 TypeScript의 타입 표기다.

이러한 타입 표기는 일반적인 JavaScript 실행 코드에 그대로 남지 않는다.

### 1.2 타입 검사기(Type Checker)

타입 검사기는 코드에서 타입이 올바르게 사용되었는지 검사한다.

주요 기능은 다음과 같다.

1. 변수와 식별자의 타입 확인
2. 값이 변수에 할당 가능한지 확인
3. 함수 인자와 반환값의 타입 확인
4. 타입 추론(Type Inference)
5. 타입 간 호환성 검사

예를 들어 다음 코드에서는 타입 오류가 발생한다.

```typescript
let age: number = 20;

age = "twenty";
// Error: Type 'string' is not assignable to type 'number'.
```

TypeScript의 타입 검사는 일반적으로 컴파일 시점에 수행된다. 타입 오류가 있더라도 설정에 따라 JavaScript 출력 자체는 가능할 수 있다.

### 1.3 컴파일러(Compiler)

컴파일러는 TypeScript 코드를 분석하고 JavaScript 코드를 출력하는 역할을 한다.

주요 작업은 다음과 같다.

- 소스 코드 읽기
- AST 생성
- 심볼 구성 및 타입 검사
- 필요한 코드 변환
- JavaScript 파일 출력

TypeScript의 타입 표기는 일반적으로 JavaScript 출력 과정에서 제거된다.

```typescript
const name: string = "Jade";
```

컴파일 결과:

```javascript
const name = "Jade";
```

TypeScript는 전통적인 의미의 전처리기(Preprocessor)와는 다르다. 따라서 컴파일러를 단순히 Pre-Compiler라고 부르는 것은 정확하지 않다.

### 1.4 IDE 언어 지원(Language Service)

TypeScript는 IDE와 에디터가 코드 작성 기능을 제공할 수 있도록 언어 서비스를 지원한다.

주요 기능은 다음과 같다.

- 자동 완성
- 타입 정보 표시
- 오류 진단
- 정의로 이동
- 이름 변경(Refactoring)
- 코드 탐색

### 1.5 전체 흐름

```text
TypeScript 코드 작성
        |
        v
타입 분석 및 검사
        |
        v
필요한 코드 변환
        |
        v
JavaScript 출력
        |
        v
브라우저 또는 Node.js에서 실행
```

핵심은 **타입을 이용해 코드를 검사하고, 실행 환경에서 사용할 수 있는 JavaScript를 출력하는 것**이다.

## 2. TSC(TypeScript Compiler)

TSC는 TypeScript 컴파일러를 실행하는 명령어다.

TypeScript 컴파일러 API를 이용하면 프로그램을 직접 생성하고 타입 검사 및 코드 출력을 제어할 수도 있다.

```typescript
import * as ts from "typescript";

const files = ["./src/index.ts"];

const options: ts.CompilerOptions = {
  target: ts.ScriptTarget.ES2022,
  module: ts.ModuleKind.ESNext,
  strict: true
};

const program = ts.createProgram(files, options);

const checker = program.getTypeChecker();

program.emit();
```

위 코드는 TypeScript 컴파일러 API를 사용하는 간단한 예시다.

- `ts.createProgram()`은 컴파일 대상 파일과 설정을 바탕으로 프로그램을 생성한다.
- `program.getTypeChecker()`는 타입 검사기를 가져온다.
- `program.emit()`은 설정에 따라 출력 파일을 생성한다.

실제 프로젝트에서는 보통 `tsconfig.json`과 `tsc` 명령어를 사용한다.

```bash
npx tsc --init
npx tsc
```

`npx tsc --init`은 기본 `tsconfig.json` 파일을 생성한다.

`npx tsc`는 설정 파일을 읽고 타입 검사와 JavaScript 출력을 수행한다. 단, `noEmit: true`가 설정되어 있으면 JavaScript 파일을 출력하지 않는다.

## 3. TypeScript의 컴파일 과정

TypeScript 컴파일러는 대략 다음과 같은 단계로 동작한다.

```text
tsconfig.json 및 컴파일 옵션 확인
        |
        v
소스 파일 수집 및 모듈 해석
        |
        v
Scanning / Tokenizing
        |
        v
Parsing
        |
        v
AST 생성
        |
        v
Binding
        |
        v
Type Checking
        |
        v
Transformation
        |
        v
Emit
```

실제 내부 동작은 설정과 코드에 따라 달라질 수 있으며, 모든 단계가 항상 단순한 일직선으로 한 번씩만 실행되는 것은 아니다.

### 3.1 설정과 소스 파일 읽기

컴파일러는 `tsconfig.json`과 명령행 옵션을 바탕으로 컴파일 대상과 옵션을 결정한다.

예를 들어 다음과 같은 옵션을 읽는다.

- `target`
- `module`
- `moduleResolution`
- `strict`
- `include`
- `exclude`
- `outDir`

또한 소스 코드에서 가져오는 모듈과 타입 선언을 해석한다.

### 3.2 Scanning / Tokenizing

소스 코드를 토큰(Token) 단위로 분석한다.

### 3.3 Parsing

토큰을 바탕으로 코드의 문법 구조를 분석하고 AST(Abstract Syntax Tree)를 생성한다.

### 3.4 Binding

AST의 선언 정보를 바탕으로 심볼(Symbol)을 구성하고 식별자가 어떤 선언을 가리키는지 연결한다.

### 3.5 Type Checking

타입 추론과 타입 호환성 검사를 수행한다.

### 3.6 Transformation

JavaScript로 출력하기 위해 필요한 변환을 수행한다.

대표적인 예는 TypeScript 타입 표기를 제거하는 것이다.

### 3.7 Emit

최종 결과를 파일로 출력한다.

대표적인 출력 파일은 다음과 같다.

- `.js`: JavaScript 코드
- `.d.ts`: 타입 선언 파일. `declaration` 옵션이 활성화된 경우 생성될 수 있다.
- `.js.map`: JavaScript와 원본 소스의 연결 정보를 담는 소스 맵 파일. `sourceMap` 옵션 등에 따라 생성된다.

모든 프로젝트가 위 파일을 전부 생성하는 것은 아니다.

## 4. AST(Abstract Syntax Tree)

AST는 소스 코드의 문법 구조를 트리 형태로 표현한 자료 구조다.

예를 들어 다음 코드를 보자.

```typescript
const x: string = "Jade";
let y: number = 1;
```

컴파일러는 이 코드를 분석해 대략 다음과 같은 구조를 만든다.

```text
SourceFile
├── VariableStatement
│   └── VariableDeclarationList
│       └── VariableDeclaration
│           ├── Identifier: x
│           ├── Type: string
│           └── Initializer: "Jade"
└── VariableStatement
    └── VariableDeclarationList
        └── VariableDeclaration
            ├── Identifier: y
            ├── Type: number
            └── Initializer: 1
```

이 트리는 개념을 이해하기 위한 단순화된 예시다. 실제 TypeScript AST의 노드 종류와 구조는 이보다 더 상세하다.

### 4.1 AST가 필요한 이유

컴파일러는 소스 코드를 단순한 문자열로만 처리하지 않는다.

AST를 사용하면 다음과 같은 작업을 수행할 수 있다.

- 변수 선언 분석
- 함수와 클래스 구조 분석
- 타입 표기 확인
- 코드 변환
- 문법 오류 진단

예를 들어 `const x: string = "Jade"`를 AST로 표현하면 변수 이름, 타입 표기, 초기화 표현식을 각각 구분해서 다룰 수 있다.

### 4.2 실제 AST 확인하기

TypeScript Compiler API를 이용하면 AST를 탐색할 수 있다.

```typescript
import ts from "typescript";

const source = `
const x: string = "Jade";
let y: number = 1;
`;

const sourceFile = ts.createSourceFile(
  "example.ts",
  source,
  ts.ScriptTarget.Latest,
  true
);

function visit(node: ts.Node) {
  console.log(
    ts.SyntaxKind[node.kind],
    node.getText(sourceFile)
  );

  ts.forEachChild(node, visit);
}

visit(sourceFile);
```

위 코드는 AST의 각 노드 종류와 해당 노드의 소스 코드를 출력하는 간단한 예시다.

실제 AST 덤프에는 `pos`, `end`, `flags`, `kind`, `locals` 등 다양한 내부 정보가 포함될 수 있다. 이 값들은 AST의 위치, 종류, 상태 및 심볼 관련 정보를 표현한다.

## 5. 토크나이징과 파싱

### 5.1 토크나이징(Scanning)

토크나이징은 소스 코드를 토큰 단위로 구분하는 과정이다.

예를 들어 다음 코드가 있다고 하자.

```typescript
const msg: string = "Hello, world";
```

이를 개념적으로 구분하면 다음과 같다.

| 토큰 종류 | 내용 |
|---|---|
| `ConstKeyword` | `const` |
| `Identifier` | `msg` |
| `ColonToken` | `:` |
| `StringKeyword` | `string` |
| `EqualsToken` | `=` |
| `StringLiteral` | `"Hello, world"` |
| `SemicolonToken` | `;` |

공백과 주석도 필요한 경우 Trivia로 처리된다. 위 표는 이해를 위한 요약이며 실제 Scanner의 모든 토큰을 나열한 것은 아니다.

### 5.2 파싱(Parsing)

파싱은 토큰을 바탕으로 문법 구조를 분석하는 과정이다.

예를 들어 다음 코드를 살펴보자.

```typescript
const msg: string = "Hello, world";
```

파싱을 통해 대략 다음과 같은 구조를 만든다.

```text
VariableStatement
└── VariableDeclarationList
    └── VariableDeclaration
        ├── Identifier: msg
        ├── Type: string
        └── Initializer: "Hello, world"
```

토크나이징이 문자를 토큰으로 구분하는 과정이라면, 파싱은 그 토큰들이 어떤 문법 구조를 이루는지 파악하는 과정이다.

## 6. 바인딩과 심볼 테이블

### 6.1 바인딩(Binding)이란?

바인딩은 AST에 존재하는 선언 정보를 바탕으로 심볼(Symbol)을 구성하고 식별자를 선언과 연결하는 과정이다.

심볼은 변수, 함수, 클래스 등 프로그램에서 선언된 대상에 관한 정보를 표현한다.

예를 들어 다음 코드를 보자.

```typescript
const msg: string = "Hello, world";

function welcome(str: string) {
  console.log(str);
}
```

컴파일러는 `msg`, `welcome`, `str` 등의 선언을 분석하고 심볼을 구성한다.

개념적으로는 다음과 같이 표현할 수 있다.

```text
Global Scope
├── msg
└── welcome
    └── Function Scope
        └── str
```

실제 스코프와 심볼 구조는 코드의 모듈 여부, 블록 구조, 함수 중첩 등에 따라 더 복잡해질 수 있다.

### 6.2 심볼 테이블(Symbol Table)

심볼 테이블은 선언된 대상과 그 정보를 관리하는 자료 구조다.

심볼이 만들어지는 대상은 변수와 함수뿐만 아니라 다음과 같은 것들도 포함한다.

- 변수
- 함수
- 클래스
- 인터페이스
- 타입 별칭
- 모듈
- 매개변수

따라서 심볼 테이블이 정확히 두 종류인 함수 선언과 변수 선언만으로 구성된다고 이해하면 안 된다.

### 6.3 같은 이름이라도 스코프가 다르면 별개의 선언일 수 있다

```typescript
let value = "hello";

function example(value: number) {
  value.toFixed();
}

example(10);
```

위 코드에는 이름이 같은 `value`가 두 개 존재한다.

- 전역 스코프의 `value`: 문자열 값으로 초기화된다.
- 함수 매개변수 `value`: `number` 타입이다.

함수 안의 `value`는 매개변수 선언을 가리키며 바깥의 `value`와는 별개다.

이처럼 컴파일러는 스코프와 바인딩 정보를 이용해 어떤 식별자가 어떤 선언을 참조하는지 판단한다.

### 6.4 타입 추론과 `any`, `unknown`

다음 코드를 살펴보자.

```typescript
let value;

value = "hello";
value = 10;
```

`let value;`처럼 타입과 초기값이 모두 없는 변수는 일반적인 설정에서 `any`로 취급될 수 있다. 정확한 동작은 `noImplicitAny`와 문맥에 따라 달라질 수 있다.

중요한 점은 `any`와 `unknown`이 같은 타입이 아니라는 것이다.

- `any`: 타입 검사를 사실상 우회한다.
- `unknown`: 어떤 값이든 받을 수 있지만 사용하기 전에 타입을 확인해야 한다.

둘 다 모든 값을 받을 수 있는 상황에서 쓰일 수 있지만, 타입 안전성 측면에서는 차이가 크다.

### 6.5 함수 내부의 타입과 외부 변수의 타입

다음 코드를 보자.

```typescript
let value = "hello";

function example(n: number) {
  let value = n;

  value.toFixed();
}

example(10);

value.toFixed();
// Error: Property 'toFixed' does not exist on type 'string'.
```

함수 안에서 선언한 `value`는 바깥의 `value`와 다른 변수다.

함수 안의 `value`는 `number`로 추론되므로 `toFixed()`를 사용할 수 있다.

바깥의 `value`는 `string`으로 추론되므로 숫자 전용 메서드인 `toFixed()`를 사용할 수 없다.

이 예시는 스코프와 타입 추론이 서로 다른 역할을 한다는 점을 보여준다.

## 7. 타입 검사 시스템

Type Checker는 프로그램에서 타입이 올바르게 사용되었는지 검사한다.

주요 작업은 다음과 같다.

### 7.1 타입 비교(Type Compatibility)

타입 검사기는 두 타입이 서로 호환되는지 판단한다.

```typescript
let age: number = 20;

age = 30;      // 정상
age = "thirty"; // 오류
```

`number` 타입에는 숫자를 할당할 수 있지만 문자열은 할당할 수 없다.

TypeScript 내부에서는 타입 관계와 다양한 플래그, 심볼 및 타입 정보를 이용해 호환성을 판단한다. 타입 비교를 단순히 비트 연산만으로 수행한다고 이해하면 부정확하다.

### 7.2 타입 추론(Type Inference)

타입 추론은 타입을 명시하지 않은 경우에도 문맥과 초기값 등을 통해 타입을 추론하는 기능이다.

```typescript
const name = "Jade";
let age = 20;

age = 21;
```

일반적으로 다음과 같이 추론된다.

- `name`: 문자열 리터럴 `"Jade"`에 해당하는 타입
- `age`: `number`

`const`와 `let`은 선언 방식이 다르기 때문에 리터럴 타입 추론에서도 차이가 발생할 수 있다.

### 7.3 함수의 매개변수와 반환 타입 검사

```typescript
function add(a: number, b: number): number {
  return a + b;
}

add(1, 2);       // 정상
add("1", "2");   // 오류
```

타입 검사기는 함수에 전달되는 인자의 타입과 함수 내부의 반환 타입을 검사한다.

### 7.4 타입 표기는 일반적으로 JavaScript 출력에서 제거된다

```typescript
function greet(name: string): string {
  return `Hello, ${name}`;
}
```

JavaScript 출력:

```javascript
function greet(name) {
  return `Hello, ${name}`;
}
```

TypeScript의 일반적인 타입 표기는 런타임에 남지 않는다. 따라서 TypeScript의 정적 타입 검사가 모든 런타임 오류를 방지하는 것은 아니다.

## 8. Transformer와 Emit

### 8.1 Transformer

Transformer는 컴파일러가 AST를 변환할 때 사용하는 단계다.

예를 들어 다음 TypeScript 코드를 보자.

```typescript
const age: number = 20;
```

JavaScript로 출력할 때 타입 표기는 제거된다.

```javascript
const age = 20;
```

`target`이 낮은 버전으로 설정된 경우에는 지원되지 않는 일부 JavaScript 문법을 변환할 수도 있다.

예를 들어 화살표 함수가 구형 문법으로 변환될 수 있다.

단, 모든 최신 JavaScript 기능이 자동으로 변환되는 것은 아니다. 특히 런타임 API의 호환성은 폴리필이나 별도 도구가 필요할 수 있다.

### 8.2 Emit

Emit은 컴파일 결과물을 출력하는 과정이다.

주요 출력물은 다음과 같다.

| 파일 | 용도 |
|---|---|
| `.js` | 실행 가능한 JavaScript |
| `.d.ts` | 타입 정보를 제공하는 선언 파일 |
| `.js.map` | 원본 코드와 출력 코드의 매핑 정보 |

어떤 파일이 출력되는지는 `declaration`, `sourceMap`, `noEmit` 등의 설정에 따라 달라진다.

### 8.3 `target`과 변환

예를 들어 다음 코드가 있다고 하자.

```typescript
const greet = (name: string) => `Hello, ${name}`;
```

`target: "ES5"`인 경우 개념적으로 다음과 같이 출력될 수 있다.

```javascript
var greet = function (name) {
  return "Hello, " + name;
};
```

`target: "ES2022"`인 경우 다음과 같이 최신 문법을 유지할 수 있다.

```javascript
const greet = (name) => `Hello, ${name}`;
```

이는 이해를 위한 예시다. 실제 변환 결과는 코드와 TypeScript 버전, 컴파일 옵션에 따라 달라질 수 있다.

## 9. `tsconfig.json`의 역할

`tsconfig.json`은 TypeScript 프로젝트의 컴파일과 타입 검사 설정을 관리하는 파일이다.

예를 들어 다음과 같은 설정을 지정할 수 있다.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "strict": true,
    "noEmit": true
  },
  "include": ["src"]
}
```

### 9.1 주요 설정

| 옵션 | 역할 |
|---|---|
| `target` | 출력할 JavaScript 문법 수준 |
| `module` | 모듈 시스템 관련 출력 및 처리 방식 |
| `moduleResolution` | 모듈과 패키지의 경로를 해석하는 방식 |
| `strict` | 엄격한 타입 검사 옵션 활성화 |
| `noEmit` | JavaScript 파일을 출력하지 않도록 설정 |
| `outDir` | 컴파일 결과물의 출력 디렉터리 |
| `rootDir` | 출력 구조를 구성할 때 기준이 되는 소스 디렉터리 |
| `declaration` | `.d.ts` 선언 파일 출력 |
| `sourceMap` | 소스 맵 생성 |
| `lib` | 사용할 JavaScript 표준 API 및 환경 타입 지정 |
| `types` | 자동으로 포함할 타입 패키지 지정 |

### 9.2 `tsconfig.json`은 어떤 파일을 컴파일할지도 결정한다

`include`, `exclude`, `files` 등을 이용해 프로젝트의 입력 파일 범위를 관리할 수 있다.

단, `exclude`는 해당 파일을 모든 상황에서 완전히 배제하는 설정은 아니다. 다른 파일에서 가져오는 등 의존 관계에 따라 컴파일 대상에 포함될 수 있다.

### 9.3 `tsc`와 번들러의 역할은 다르다

일반적인 TypeScript 프로젝트에서는 TypeScript 컴파일러와 번들러가 함께 사용될 수 있다.

예를 들어 Vite는 TypeScript 코드를 빠르게 변환하고 번들링할 수 있지만, 기본적으로 전체 TypeScript 타입 검사를 대신하지는 않는다.

따라서 실제 프로젝트에서는 `tsc --noEmit` 등을 이용해 별도로 타입 검사를 수행하기도 한다.

## 10. `target`과 `module`의 차이

이제 핵심 질문으로 돌아가 보자.

`tsconfig.json`에서 `target`과 `module`은 모두 컴파일 설정이지만, 결정하는 대상이 다르다.

- `target`: JavaScript 문법을 어느 버전까지 사용할 것인가?
- `module`: 모듈을 어떤 방식으로 처리하고 해석할 것인가?

### 10.1 핵심 차이

| 구분 | `target` | `module` |
|---|---|---|
| 역할 | JavaScript 문법 수준 지정 | 모듈 시스템 관련 설정 |
| 주요 대상 | 화살표 함수, 클래스 등 | `import`, `export` |
| 예시 | `ES2022` | `ESNext`, `CommonJS`, `NodeNext` |
| 핵심 질문 | 어떤 JavaScript 문법을 출력할까? | 모듈을 어떤 규칙으로 처리할까? |

### 10.2 `target`: JavaScript 문법의 세대

다음 코드를 보자.

```typescript
const greet = (name: string) => {
  return `Hello, ${name}`;
};
```

`target: "ES5"`인 경우:

```javascript
var greet = function (name) {
  return "Hello, " + name;
};
```

`target: "ES2022"`인 경우:

```javascript
const greet = (name) => {
  return `Hello, ${name}`;
};
```

`target`은 컴파일 결과의 JavaScript 문법 수준을 결정한다.

단, 구형 브라우저에서 최신 API를 사용할 수 있게 해주는 설정은 아니다. 최신 API를 구형 환경에서 사용하려면 별도의 폴리필 등이 필요할 수 있다.

### 10.3 `module`: 모듈을 연결하는 방식

다음 코드를 보자.

```typescript
import { sum } from "./math";

export const result = sum(1, 2);
```

`module: "CommonJS"`로 출력하는 경우:

```javascript
const math_1 = require("./math");

exports.result = (0, math_1.sum)(1, 2);
```

`module: "ESNext"`로 출력하는 경우:

```javascript
import { sum } from "./math";

export const result = sum(1, 2);
```

실제 출력 형태는 코드와 설정에 따라 달라질 수 있다.

CommonJS는 `require()`와 `exports`를 사용하는 모듈 시스템이고, ESM은 `import`와 `export`를 사용하는 표준 모듈 시스템이다.

### 10.4 `module`은 외부 라이브러리만을 위한 설정이 아니다

예를 들어 프로젝트 내부에 다음 두 파일이 있다고 하자.

`math.ts`

```typescript
export const sum = (a: number, b: number) => a + b;
```

`main.ts`

```typescript
import { sum } from "./math";

console.log(sum(1, 2));
```

외부 라이브러리를 설치하지 않았더라도 파일 간에 `import`와 `export`를 사용한다.

따라서 `module` 설정은 외부 라이브러리를 가져오는 경우에만 필요한 것이 아니다.

외부 라이브러리의 배포 형식과 호환성에도 영향을 주지만, 프로젝트 자체의 모듈 처리 방식도 결정한다.

### 10.5 `target`과 `module`은 독립적으로 설정할 수 있다

예를 들어 다음 설정이 가능하다.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "CommonJS"
  }
}
```

이 설정은 최신 JavaScript 문법을 유지하면서 CommonJS 모듈 방식으로 출력하는 조합이다.

반대로 다음 설정도 가능하다.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ES2022"
  }
}
```

이 경우 JavaScript 문법 수준과 모듈 형식 모두 ES2022를 기준으로 설정한다.

다만 `module`은 단순히 `import`를 어떤 문자열로 바꾸는 옵션만은 아니다. 모듈 해석 방식에도 영향을 줄 수 있고, Node.js에서는 `package.json`의 `"type"`이나 파일 확장자 같은 설정도 실제 실행 방식에 영향을 준다.

### 10.6 왜 굳이 분리했을까?

JavaScript 문법의 버전과 모듈 시스템은 서로 다른 문제이기 때문이다.

예를 들어 기존 Node.js 시스템이 CommonJS를 사용하더라도 최신 JavaScript 문법을 사용하고 싶을 수 있다.

이때 다음과 같이 설정할 수 있다.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "CommonJS"
  }
}
```

반면 최신 브라우저와 번들러 기반 프로젝트에서는 ESM을 사용할 수 있다.

따라서 분리의 이유는 레거시 코드와의 호환성만이 아니다.

- 실행 환경의 차이
- 모듈 시스템의 차이
- 번들러의 모듈 해석 방식
- 라이브러리의 배포 형식

이러한 차이를 독립적으로 설정할 수 있도록 분리되어 있다.

### 10.7 `moduleResolution`은 또 다른 설정이다

`module`과 함께 자주 등장하는 설정이 `moduleResolution`이다.

```json
{
  "compilerOptions": {
    "module": "ESNext",
    "moduleResolution": "bundler"
  }
}
```

`module`이 모듈 시스템 관련 출력 및 처리 방식을 지정한다면, `moduleResolution`은 `import` 경로와 패키지를 어떻게 찾아서 해석할지 결정한다.

예를 들어 Vite 같은 번들러를 사용하는 환경과 Node.js가 직접 모듈을 실행하는 환경은 모듈 해석 규칙이 다를 수 있다.

## 11. 실행 환경에 따라 설정이 달라지는 이유

새로운 프로젝트를 시작한다고 생각해 보자.

TypeScript를 설치하고 `npx tsc --init`을 실행하면 설정 파일을 만들 수 있다.

하지만 TypeScript를 설치했다고 해서 실행 환경까지 결정되는 것은 아니다.

JavaScript를 어디에서 실행할 것인지에 따라 적절한 설정이 달라진다.

### 11.1 프런트엔드 프로젝트

예: React + Vite

- 브라우저에서 실행된다.
- Vite가 개발 서버와 번들링을 담당한다.
- 브라우저 API 타입이 필요하다.
- 번들러의 모듈 해석 방식에 맞추는 것이 일반적이다.

예시:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "jsx": "react-jsx",
    "strict": true,
    "noEmit": true
  }
}
```

### 11.2 백엔드 프로젝트

예: NestJS + Node.js

- Node.js에서 실행된다.
- Node.js의 모듈 시스템에 맞춰야 한다.
- 브라우저 전용 타입이 필요하지 않을 수 있다.
- 데코레이터, 의존성 주입 등에 필요한 설정이 있을 수 있다.

NestJS 프로젝트는 CLI가 생성한 설정을 먼저 확인하는 것이 좋다. 기존 프로젝트가 CommonJS를 사용한다면 무조건 `NodeNext`로 바꾸기보다는 기존 설정과 실행 방식을 유지하는 편이 안전할 수 있다.

### 11.3 기술 스택의 권장 설정이란?

기술 스택의 권장 설정이란 무조건 최신 버전을 사용하는 것이 아니다.

**해당 프레임워크, 빌드 도구, 실행 환경이 기대하는 규칙에 맞춰 설정하는 것**을 의미한다.

따라서 모든 프로젝트의 `target`과 `module`을 무조건 동일하게 설정할 필요는 없다.

## 12. React + Vite + NestJS 프로젝트 설정

React + Vite 프런트엔드와 NestJS 백엔드를 함께 사용하는 경우를 살펴보자.

예를 들어 하나의 저장소에서 다음과 같이 관리할 수 있다.

```text
my-project/
├── apps/
│   ├── web/
│   │   ├── src/
│   │   ├── package.json
│   │   └── tsconfig.json
│   └── api/
│       ├── src/
│       ├── package.json
│       └── tsconfig.json
├── package.json
└── tsconfig.json
```

이러한 구성을 모노레포(Monorepo) 방식으로 관리할 수 있다.

### 12.1 프런트엔드: React + Vite

프런트엔드는 브라우저에서 실행되고 Vite가 모듈을 처리한다.

일반적인 설정 예시:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "jsx": "react-jsx",
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

각 옵션의 역할은 다음과 같다.

| 옵션 | 이유 |
|---|---|
| `target` | 브라우저에서 사용할 JavaScript 문법 수준 지정 |
| `module` | ES 모듈 방식 사용 |
| `moduleResolution` | Vite 등 번들러의 모듈 탐색 방식에 맞춤 |
| `lib` | JavaScript 표준 API와 브라우저 API 타입 제공 |
| `jsx` | React JSX 처리 방식 지정 |
| `strict` | 엄격한 타입 검사 활성화 |
| `noEmit` | TypeScript가 JavaScript 파일을 출력하지 않도록 설정 |
| `skipLibCheck` | 의존성의 선언 파일 검사 부담을 줄임 |

실제 프로젝트에서는 Vite가 생성한 기본 설정을 우선 확인하고 필요한 부분만 변경하는 것이 좋다.

### 12.2 백엔드: NestJS

NestJS는 Node.js에서 실행된다. 모듈 시스템은 프로젝트가 ESM을 사용하는지 CommonJS를 사용하는지에 맞춰야 한다.

Node.js의 ESM을 사용하는 경우 설정 예시는 다음과 같다.

```json
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "target": "ES2022",
    "lib": ["ES2022"],
    "types": ["node"],
    "strict": true,
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true,
    "esModuleInterop": true,
    "sourceMap": true,
    "outDir": "./dist",
    "skipLibCheck": true
  }
}
```

단, 이 설정을 기존 NestJS 프로젝트에 그대로 덮어쓰는 것은 권장하지 않는다. `NodeNext`는 Node.js의 모듈 규칙과 연동되며, TypeScript 버전과 프로젝트의 `package.json` 설정에 따라 동작이 달라진다.

특히 `NodeNext`를 사용할 때는 다음을 함께 확인해야 한다.

- `package.json`의 `"type"` 설정
- `.js`, `.mjs`, `.cjs` 등 파일 확장자 규칙
- 상대 경로 import의 확장자
- NestJS의 빌드 설정
- 실제 Node.js 실행 방식

NestJS CLI가 생성한 `tsconfig.json`과 `tsconfig.build.json`을 기준으로 유지하는 것이 안전하다.

### 12.3 공통 설정과 개별 설정

프런트엔드와 백엔드는 일부 옵션을 공유할 수 있지만, 모든 설정을 하나로 통일할 필요는 없다.

예를 들어 두 환경 모두 `strict: true`를 사용할 수 있다.

반면 다음과 같은 옵션은 환경에 따라 달라질 수 있다.

| 옵션 | 프런트엔드 | 백엔드 |
|---|---|---|
| `module` | `ESNext` 등 | `NodeNext` 또는 기존 CommonJS 설정 |
| `moduleResolution` | `bundler` | `NodeNext` 또는 NestJS 기본 설정 |
| `lib` | `DOM` 포함 | 일반적으로 브라우저 DOM 제외 |
| `jsx` | React 설정 필요 | 보통 불필요 |
| `noEmit` | Vite가 변환하므로 사용 가능 | 빌드 방식에 따라 결정 |

### 12.4 설정을 나누는 이유

프런트엔드와 백엔드가 서로 다른 실행 환경을 사용하기 때문이다.

- 프런트엔드는 브라우저 API와 번들러를 고려한다.
- 백엔드는 Node.js의 모듈 시스템과 실행 규칙을 고려한다.
- 공통 코드는 두 환경에서 모두 사용할 수 있는 API와 타입을 기준으로 설계한다.

`target`을 반드시 다르게 지정해야 하는 것은 아니다. 두 환경 모두 ES2022를 목표로 삼을 수 있지만, 모듈 해석과 실행 방식은 서로 다를 수 있다.

## 13. 핵심 요약

### TypeScript의 내부 구조

- **프로그래밍 언어:** 타입 표기와 다양한 언어 기능 제공
- **Type Checker:** 타입 추론 및 타입 호환성 검사
- **Compiler:** 코드 분석, 변환, JavaScript 출력
- **Language Service:** 자동 완성, 오류 진단, 코드 탐색 지원

### 컴파일 과정

```text
설정 및 소스 파일 읽기
    → Scanning
    → Parsing
    → AST 생성
    → Binding
    → Type Checking
    → Transformation
    → Emit
```

### `target`과 `module`

- `target`: JavaScript 문법 수준을 결정한다.
- `module`: 모듈 시스템과 관련된 출력 및 처리 방식을 결정한다.
- `moduleResolution`: 모듈과 패키지를 어떤 규칙으로 찾을지 결정한다.

### 실무에서 기억할 것

1. 최신 JavaScript 문법을 사용한다고 해서 반드시 ESM을 사용해야 하는 것은 아니다.
2. `target`과 `module`은 서로 다른 문제이므로 독립적으로 설정할 수 있다.
3. 레거시 호환성은 설정을 분리하는 이유 중 하나지만 유일한 이유는 아니다.
4. Vite와 NestJS는 서로 다른 실행 환경을 사용하므로 설정을 분리하는 것이 일반적이다.
5. 새로운 프로젝트에서는 프레임워크가 생성한 기본 설정을 확인하고 필요한 부분만 수정한다.
6. TypeScript의 타입 검사는 런타임 검증을 완전히 대체하지 않는다.

**한 문장으로 기억하기:**

`target`은 JavaScript 문법의 세대, `module`은 모듈 처리 방식, `moduleResolution`은 모듈을 찾는 규칙이다.
